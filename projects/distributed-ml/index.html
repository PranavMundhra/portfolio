Distributed-ML

A distributed inference platform: one gateway, multiple CPU workers, and a trace of every request's path.

What exists today

A FastAPI gateway and two registered CPU workers run as separate processes. The gateway routes each prediction round-robin among workers that advertise the requested model, and serves three fixed models: Iris classification, house-price regression, and male/female face-image classification (the last two as ONNX).

Workers register themselves and send heartbeats, so the gateway detects silent workers and stops routing to them. Lamport clocks stamp each request, so the UI can show the exact path and ordering of every prediction. A worker dashboard shows live status, and the system distinguishes unavailable workers (503), timeouts (504), and invalid responses (502).

It also runs across two PCs on a local network: the gateway and one worker on one machine, a second worker on another. The repository was started on 11 October 2026 and has grown through six verified milestones, most recently the LAN launchers on 24 October.

Request flow

Each model has its own request and response contract, checked at both the gateway and the worker. The gateway keeps a separate round-robin cursor per model, so a worker is only chosen if it has loaded the model being requested. Python, FastAPI, Pydantic, HTTPX, ONNX Runtime, scikit-learn, and pytest support the platform.

Failure detection

Workers send a heartbeat every 2 seconds. If the gateway sees neither a registration nor an accepted heartbeat for 8 seconds, it marks that worker unavailable and new requests skip it. A health probe or a prediction cannot renew an expired lease, so only a real heartbeat brings a worker back.

Stale or out-of-order heartbeats and messages from an old process instance are rejected, and workers re-register on their own after the gateway restarts. A dashboard control can pause a worker to demonstrate this live, and the smoke scripts also stop and restart real worker processes.

Tracing with Lamport clocks

Each gateway and worker process keeps a logical counter that increases when it sends a message and merges as max(local, remote) + 1 when it receives one. Every prediction in the interface shows a six-event trace with those timestamps and the identity of each process that handled it.

Traces carry no feature or image data. The gateway keeps the latest 200, and failures produce explicit partial traces. The timestamps describe ordering, not milliseconds or synchronised physical clocks.

Why logical clocks: the wall clocks of two separate PCs can't be compared, so their timestamps can't order events. A logical counter gives every request a trace whose causal order can be checked on any machine. The gateway already sees every request, so the clocks add little to routing itself. I included them to make cross-machine ordering visible and verifiable, and as a distributed-systems learning goal.

Running across two PCs

The LAN setup puts the gateway and Worker 1 on PC 1 and Worker 2 on PC 2. Each worker holds its own copy of the three models, and each request runs entirely on one worker, so only the request and its result cross the network.

  • Launchers: a single command starts the gateway or a worker on a chosen private LAN address. It refuses localhost, wildcard and public addresses, checks that the address belongs to the PC and that the port is free, and lets a worker test its connection to the gateway before it starts.
  • Verification: a checker waits for both workers to register and send heartbeats, and requires two distinct worker addresses. It then sends 24 real predictions, six each for Iris, house price and two face-image samples. Each group must alternate 3 and 3 between the workers, and every response must carry a valid six-event Lamport trace.
  • Failure demo: stopping Worker 2 on PC 2 lets its heartbeat expire after about 8 seconds, after which new requests go to Worker 1. Restarting Worker 2 brings it back into the rotation.
  • Network setup: the guide covers the Windows firewall rules, a port-reachability test in both directions, and the case where a Wi-Fi network isolates its clients.

The three models

The house-price model uses six inputs: living area, bedrooms, full bathrooms, garage spaces, year built, and overall quality. It predicts historical US prices, not current Indian prices, and its R² is not a percentage accuracy. Each worker loads its own local copy of the ONNX files, and a worker with a missing or broken file keeps serving Iris.

Validation

The repository's latest recorded run passes 361 tests covering gateway routing, worker registration, heartbeats, Lamport traces, the fixed models, the dashboard, the LAN launchers, and the UI. Separate smoke scripts start real gateway and worker processes and check alternating routing, heartbeat expiry, survivor routing, worker restart, and gateway restart recovery.

The LAN tooling has its own 35 tests, plus a scripted rehearsal that starts real gateway and worker processes on a private interface, checks routing and traces, stops and restarts a worker, and restarts the gateway. These results are as recorded in the repository; I have not re-run them for this page.

Current boundaries

The setup is deliberately small: one gateway and one worker per PC, on a trusted local network.

  • The gateway is a single point of failure by design, because leader election was left out of scope, and its worker registry lives in memory.
  • A failed prediction is returned without retry; only new requests avoid the failed worker.
  • Model files are copied to each worker by hand. There is no automatic model distribution yet.
  • Uploading an image is an inference input, not a new model. Public model upload, authentication and arbitrary model schemas are deferred.
  • Latency, throughput and recovery-time benchmarks have not been run, and least-loaded scheduling is not implemented.

Future direction

My goal is a shared inference platform where users can submit their trained models and other users can run predictions without installing those models on their own systems. The next steps are latency and throughput benchmarks, and retry and failover for in-flight requests, before model upload is attempted.
